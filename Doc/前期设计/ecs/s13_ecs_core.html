13. ECS 架构 · EnTT + BlobStorage 混合

✔ 已确认

13.1 设计核心：数据形状决定数据归属

不是"C++ 层实现 ECS 最好"，而是每组数据的 遍历宽度 和 逻辑复杂度 决定它的存储位置。 宽遍历（1000+ 实体/简单公式）→ C++ EnTT SoA 布局，利用 cache 友好和 SIMD。 深逻辑（少量实体/复杂分支）→ daslang BlobStorage，利用热更新和类型灵活性。 真理之源原则：每个 Component 只在一层拥有写入权，绝不在两层同时写同一个组件。 C++ 引擎以 EnTT 管理 Entity 生命周期和高频 C++ 组件（SOA 布局）。 脚本层定义的组件通过 ScriptComponentStorage（并行 SoA blob 列）独立存储。 脚本 API 采用 DECS 风格语法——声明式 ecs_query / 引用直改 ecs_edit / Stage 组织 ecs_stage， 底层自动路由到 EnTT storage 或 BlobStorage，对脚本开发者透明。 零宏：C++ Component 一行模板函数注册，脚本 Component 一个 struct 注解即可。

⚠ EnTT View 迭代顺序说明： EnTT v4.0 的 view 迭代器从后往前遍历 packed array（反向迭代）。 这是 EnTT 为支持在迭代中安全删除（swap_and_pop）而做的设计决策—— 反向遍历保证新 swap 进来的元素已被遍历过，不会漏掉。 因此ecs_query 不保证遍历顺序，同帧内所有修改应视为一个原子快照。 业务逻辑不应依赖实体的迭代先后——调试复现应使用 registry snapshot 而非迭代顺序。
决策维度C++ EnTTDasLang BlobStorage
每 Tick 遍历实体数1000+（全场景）< 100（仅相关实体）
操作复杂度简单公式、线性计算多分支、状态机、业务规则
热更新需求低（引擎级，稳定后不变）高（策划迭代、运营调整）
典型 ComponentPosition, Velocity, Health, ColliderQuestProgress, BuffState, TradeRecord, SkillCooldown
内存布局EnTT SoA 分页（cache 友好）ScriptComponentStorage SoA Blob
写入权C++ System 独占写入DasLang System 独占写入

13.2 Scene 类：EnTT + BlobStorage（调整）

// Scene.h — 每个场景独立
class Scene {
public:
    Scene(uint32_t sceneId) : _sceneId(sceneId) {}

    // Entity 生命周期 — EnTT 管理
    Entity CreateEntity() {
        auto e = _ecsRegistry.create();
        return Entity{_sceneId, uint32_t(e)};
    }
    void DestroyEntity(Entity we) {
        for (auto& [name, storage] : _scriptStorages)
            storage->Remove(we.entityId);
        _ecsRegistry.destroy(entt::entity(we.entityId));
    }
    bool IsValid(Entity we) const {
        return _ecsRegistry.valid(entt::entity(we.entityId));
    }

    // C++ 组件 — 直接走 EnTT storage
    template<typename T> T& GetComponent(Entity we);
    template<typename T> auto& EnTTStorage();

    // 多组件暴露 — ecs_query 底层
    template<typename... Components>
    auto CreateView() { return _ecsRegistry.view<Components...>(); }

    // 脚本组件 — 运行时注册 + SoA blob 存储
    void RegisterScriptComponent(const std::string& name, size_t componentSize);
    ScriptComponentStorage* GetScriptStorage(const std::string& name);

    entt::registry& EcsRegistry() { return _ecsRegistry; }

    // 脏标记 — 网络复制使用
    template<typename T> void MarkDirty(const Entity& we);
    template<typename T> bool IsDirty(const Entity& we) const;

private:
    uint32_t _sceneId;
    entt::registry _ecsRegistry;  // C++ 组件（Position/Velocity/Health...）
    std::unordered_map<std::string, std::unique_ptr<ScriptComponentStorage>> _scriptStorages;
};

13.3 ScriptComponentStorage — 脚本组件的 SoA blob 列

class ScriptComponentStorage {
public:
    ScriptComponentStorage(std::string name, size_t componentSize)
        : _name(std::move(name)), _stride(componentSize) {}

    bool Has(uint32_t entityId) const { return _sparse.contains(entityId); }
    void* GetPtr(uint32_t entityId) { return _data.data() + _sparse.at(entityId) * _stride; }

    void Emplace(uint32_t entityId, const void* src);      // 存在则原地覆盖
    void Remove(uint32_t entityId);                       // swap-with-last O(1)

    const uint8_t* DataPtr() const { return _data.data(); }  // 给 DasLang temp array 暴露指针
    size_t Count() const { return _data.size() / _stride; }

private:
    std::string _name;
    size_t _stride;
    std::vector<uint8_t> _data;                              // SoA blob 数据
    std::unordered_map<uint32_t, uint32_t> _sparse;  // entityId → index
};

13.4 C++ Component 注册（零宏 + 两种桥接模式）

每个 C++ Component 在 Module 构造函数中一行注册。自动生成跨语言结构映射，支持两种运行模式。 

template<typename T>
void RegisterEcsComponent(Module& mod, ModuleLibrary& lib, const char* dasName) {
    mod.addAnnotation(new ManagedStructureAnnotation<T, true>(dasName, lib));
    // + addExtern: ecs_query_get_{T} / ecs_edit_get_{T} / ecs_edit_set_{T} / ecs_view_{T}
}

// Module 构造函数 — 一行注册一个 Component
ModuleEntt() : Module("ecs") {
    ModuleLibrary lib(this);
    lib.addBuiltInModule();
    RegisterEcsComponent<Position>(*this, lib, "Position");
    RegisterEcsComponent<Velocity>(*this, lib, "Velocity");
    RegisterEcsComponent<Health>(*this, lib, "Health");
    RegisterEcsComponent<Mana>(*this, lib, "Mana");
}

两种桥接模式

模式适用场景底层实现
ecs_query — 声明式批量遍历 每 Tick 遍历全部拥有某组件的实体 EnTT View → daslang temp array 包装 EnTT dense buffer（零拷贝引用）
ecs_edit — ComponentMap 单实体操作 处理消息/事件，操作 1 个实体的多个组件 registry.get<T>(e) 返回引用 → ComponentMap 字段聚合（直接写 EnTT/BlobStorage）

13.5 遍历：ecs_query 与 ecs_edit 两种模式

模式 1：ecs_query — 声明式批量遍历（替代 ecs_view）

脚本声明需要的组件列表，宏在编译期展开为 EnTT owning group。 owning group 保证所有 owned 组件的 storage 前 N 个位置严格对齐（同一entity 在同一索引）， raw() 的指针可直接用于 parallel array 遍历。 循环内变量是 引用，赋值直接写入 EnTT storage，零拷贝。

⚠ 为什么不能直接用 view.storage<T>().raw()： EnTT 4.0 的 view.storage<T>() 返回的是原始 storage 指针（全量数据），不是 view 的交集子集。 Flavor A（raw() 全量 → parallel array）的结果是未对齐的——pos_arr[i] 和 vel_arr[i] 可能对应不同的 entity。 正确的做法是用 owning group： registry.group<owned_t<Position, Velocity>>() 在 on_construct / on_destroy 时物理重排 storage， 保证 group.storage<Position>().raw()[0..N-1] 和 group.storage<Velocity>().raw()[0..N-1] 严格对齐（同一个 entity 在两个数组中的索引相同）。 owning group 的重排开销在创建/销毁 entity 时发生，遍历热路径零开销。 
// daslang 宏 ecs_query — 编译期展开（Flavor C：owning group）
// ecs_query(sceneId; pos : Position& ; vel : Velocity)
//   ↓ 展开为 ↓
// auto group = registry.group<entt::owned_t<Position, Velocity>>();
//   → EnTT 物理重排 storage，前 N 个元素对齐
// pos_arr = makeTempArray(group.storage<Position>().raw(), group.size());
// vel_arr = makeTempArray(group.storage<Velocity>().raw(), group.size());
// for i in range(group.size()): loop body — pos_arr[i] 和 vel_arr[i] 同一 entity

// C++ 桥接实现
template<typename... OwnedComponents>
static void EcsQueryBridge(Scene& scene,
                          const TBlock<void, array<OwnedComponents>...>& block,
                          Context* ctx, LineInfoArg* at)
{
    // owning group：owned 组件 storage 前 N 个元素严格对齐
    auto group = scene.EcsRegistry().group<
        entt::owned_t<OwnedComponents...>>();

    int32_t count = int32_t(group.size());  // 交集 entity 数量

    // group 中每个 Component 的 raw() 前 count 个 = 对齐的交集数据
    // makeTempArray 零拷贝 — daslang array 指向 EnTT 内部 paged buffer
    das_invoke<void>::invoke(ctx, at, block,
        makeTempArray<OwnedComponents>(
            group.template storage<OwnedComponents>().raw(), count)...);
}

模式 2：ecs_edit — ComponentMap 单实体操作（替代 ecs_get/set/emplace）

闭包接收 ComponentMap 对象，cmp.field.subfield 语法直接读写组件。 每个字段是 C++ 存储的引用——修改即时生效，无需三行 get/copy/set。 自动判别 EnTT 组件 vs BlobStorage 组件，路由到正确的存储。 

// C++ 端 ComponentMap 构建
// ecs_edit(entity) $(cmp) { cmp.health.current -= 10; }
//   ↓ 展开为 ↓
// auto& hp  = registry.get<Health>(entity);        // EnTT 引用
// auto* qp  = scriptStorage->GetPtr(entity);       // BlobStorage 指针
// ComponentMap cmp = {{"health", &hp}, {"questProgress", qp}};
// 闭包执行 → cmp.health 是 Health&，cmp.questProgress 是 QuestProgress*

// ecs_edit 底层桥接
struct ComponentMap {
    std::unordered_map<std::string, void*> enTTFields;    // EnTT 组件引用 → 直接是 T*
    std::unordered_map<std::string, void*> scriptFields;  // BlobStorage 组件指针
};

template<typename Func>
void EcsEditBridge(Scene& scene, Entity we, Func&& body) {
    auto e = entt::entity(we.entityId);
    ComponentMap cmp;

    // 遍历 Scene 注册的 EnTT 组件 → 每人一行 resolve
    #define RESOLVE_ENTT_FIELD(T, name) \
        if (scene.EcsRegistry().all_of<T>(e)) \
            cmp.enTTFields[name] = &scene.EcsRegistry().get<T>(e);
    RESOLVE_ENTT_FIELD(Position,  "position");
    RESOLVE_ENTT_FIELD(Health,    "health");
    RESOLVE_ENTT_FIELD(Velocity,  "velocity");
    #undef RESOLVE_ENTT_FIELD

    // 遍历 BlobStorage 组件
    for (auto& [name, storage] : scene.ScriptStorages()) {
        if (storage->Has(we.entityId))
            cmp.scriptFields[name] = storage->GetPtr(we.entityId);
    }

    body(cmp);  // 执行 daslang 闭包 → cmp 字段直接指 EnTT/BlobStorage
}

查询约束：ecs_query 带条件

支持可选的 with/without 约束——等价于 EnTT 的 include/exclude 过滤， 编译期生成正确的 View 类型。 

// 只遍历同时有 Health 和 MonsterTag 的实体
// 排除有 Dead 标记的实体
ecs_query(sceneId;
    pos     : Position&;
    vel     : Velocity;
    with    Health, MonsterTag;
    without Dead
) {
    pos.x += vel.vx * dt
}
// 展开为: registry.view<Position, Velocity>(entt::exclude<Dead>)
// 内部只遍历同时有 Health + MonsterTag + Position + Velocity 的实体

13.6 数据一致性：双缓冲（Double Buffering）模型

为保证同一 Tick 内所有 entity 看到的世界状态完全一致（解决 §1 中 ecs_query / ecs_edit 双路径的数据一致性问题），采用双缓冲共享状态方案：

缓冲区用途访问模式
current只读快照——ecs_query 读者的数据源本 Tick 内所有系统读取一致
next写入目标——所有 ecs_edit/ecs_create/ecs_destroy 的累积结果本 Tick 内修改写入此缓冲区
Tick N 开始:
  current = Tick N-1 结束时的完整状态
  next    = current 的副本（初始）

ecs_stage "movement":
  ecs_query 读 current → 写 next（Position 变更写入 next）

ecs_stage "combat":
  ecs_query 读 current → 写 next（Health 变更写入 next）
  ecs_edit 读 current → 写 next（BuffList 变更写入 next）
  → 关键：entity B 的计算不能依赖 entity A 在本 Tick 内的修改
  → 因为大家都读 current，都是基于 N-1 帧的快照

Tick N 结束:
  swap(current, next)  → 所有修改一次性生效
  next 现在 = 新状态，current = 旧状态（下一 Tick 的 next 会基于此构建）

此方案的核心价值：同一帧内，无论 ecs_query 遍历的顺序如何，无论有多少 entity 相互影响，每个 entity 看到的世界状态完全相同 (= 上一 Tick 结束时的状态)。 这保证了即使 EnTT 反向迭代、多个 Stage 交叉修改、脚本和 C++ 双路径并行访问， 结果都是确定性的。同时双缓冲天然提供 frame snapshot，用于录像回放和崩溃恢复。

内存开销：双缓冲 = 2× EnTT registry + 2× BlobStorage。以 10000 entity × 平均 500 字节组件数据估算 ≈ 10MB 额外内存。对于现代服务器（64GB+）可忽略。 实现上 next 缓冲区不会完整拷贝整个 registry——只拷贝有变更的 entity（copy-on-write 分摊）。

13.7 ecs_stage — Stage 模式组织系统执行顺序

取代手动调用函数，用 ecs_stage 声明执行顺序。 每个 Stage 内部读 current、写 next。Stage 之间 next 状态逐步累积—— 但 current 在整个 Tick 内保持不变。每 Tick 顶层调度一目了然。 

// server_tick.das — 顶层 Tick 调度
[export]
def ServerTick(sceneId : uint32; dt : float)
{
    ecs_stage "input"      { ProcessInput(sceneId) }
    ecs_stage "movement"   { SystemMovement(sceneId, dt) }
    ecs_stage "stats"      { SystemRecalcStats(sceneId) }
    ecs_stage "combat"     { SystemCombat(sceneId) }
    ecs_stage "buff"       { SystemBuffTick(sceneId, dt) }
    ecs_stage "ai"         { SystemAI(sceneId) }
    ecs_stage "quest"      { SystemQuest(sceneId) }
    ecs_stage "skill"      { SystemSkillCooldown(sceneId) }
    ecs_stage "aoi"        { SystemAOI(sceneId) }
    ecs_stage "replicate"  { SystemReplicate(sceneId) }
    ecs_stage "save"       { SystemDirtyFlush(sceneId) }
}

延迟操作与双缓冲写入

在双缓冲模型下，所有修改操作不直接写入 current，而是写入 next 缓冲区。 Tick 结束时 swap(current, next) 一次性生效。 在此期间，"未 swap 的修改"对读路径不可见——避免了"在遍历中看到已修改的数据"这类经典 bug。

13.8 Component 删除策略：混合策略

EnTT v4.0 默认使用 in_place 删除策略（tombstone + free-list）， 保证指针稳定性但会累积 tombstone。根据组件类型采用差异化策略：

组件类别策略原因示例
高频瞬态组件 swap_and_pop (in_place_delete = false) 每 Tick 频繁创建/销毁（怪物刷新/死亡），无指针稳定性需求 Position, Velocity, Health, CombatTag, StatsDirtyTag
持久状态组件 in_place（默认）+ 定期 compact ecs_edit 持有引用，需要指针稳定性；销毁频率低 Inventory, BuffList, SkillBar, AIBlackboard 
// component_traits 特化——高频瞬态 → swap_and_pop
template<>
struct entt::component_traits<Position> {
    static constexpr auto in_place_delete = false;  // 强制 swap_and_pop
};
template<> struct entt::component_traits<Velocity> { static constexpr auto in_place_delete = false; };
template<> struct entt::component_traits<Health>   { static constexpr auto in_place_delete = false; };
template<> struct entt::component_traits<CombatTag>{ static constexpr auto in_place_delete = false; };

// 持久组件保持 in_place（默认），Scene 定期检查并 compact
void Scene::CheckAndCompact() {
    constexpr float kCompactThreshold = 0.5f;  // tombstone > 50% 触发
    constexpr size_t kMinEntities = 1000;       // 太少了不值得

    for (auto&& [id, storage] : _ecsRegistry.storage()) {
        auto total = storage.size() + storage.free_list();
        if (total < kMinEntities) continue;
        float ratio = float(storage.free_list()) / float(total);
        if (ratio > kCompactThreshold) {
            storage.compact();
            LOG_WARN("Scene {} storage compacted: tombstone {:.1f}%", _sceneId, ratio * 100);
        }
    }
}

13.10 判断标准

每 Tick 需要成百上千实体批量遍历的 → C++ struct + EnTT。低频逻辑、纯业务、热更新需求 → DasLang [script_component]。

13.11 Registry 架构：单层 Scene Registry

和业界主流做法一致——只保留 SceneRegistry（每个场景一个 EnTT registry）。 GlobalRegistry 和 PersistentRegistry 被拆分为独立的 C++ 单例 Manager 和 紧凑容器， 因为它们管理的对象不需要 ECS 的 entity 生命周期和 sparse_set 存储开销。

存储层实现用途理由
SceneRegistry × N 每个 Scene 持有独立 entt::registry 玩家/怪物/NPC/掉落——所有有生命周期的场景实体 性能刚需——ecs_query 遍历时不该扫到其他场景的 entity
GuildMgr（单例） std::unordered_map<uint32_t, Guild> 公会创建/解散/成员管理/公会仓库 不是 ECS entity——不需要 create/destroy、sparse_set、view 遍历
ChatChannelMgr（单例） std::vector<ChatChannel> 世界频道/公会频道/私聊/队伍频道的消息路由
BossScheduler（单例） std::unordered_map<uint32_t, BossState> 世界 Boss 的刷新计时器/HP/阶段/参战玩家列表
MailMgr（单例） std::vector<MailMessage> 玩家邮件（发件/收件/附件/已读状态）
ConfigTable<T>（单例模板） DenseMap<uint32_t, T> 纯只读配置数据——通过 templateId 做 O(1) 查表 静态数据不需要 entity 和 sparse_set 三层间接寻址

ConfigTable 实现

ConfigTable 的权威定义见 §13c 全局 Manager 单例。 采用 shared_ptr<vector<T>> + shared_ptr<unordered_map<uint32_t,uint32_t>> 双容器方案， Find() 查索引 + 数组取值 O(1)，All() 遍历数组 O(n)。热重载用 shared_ptr 原子 swap。

Entity 简化

取消了 GlobalRegistry (sceneId=0) 和 PersistentRegistry (sceneId=0xFFFFFFFF) 的特殊值。 Entity 就单纯是 (sceneId, entityId)，只指向 Scene。 

struct Entity {
    uint32_t sceneId;   // Scene ID
    uint32_t entityId;  // EnTT entity id
};
