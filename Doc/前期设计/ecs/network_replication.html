网络复制系统 · 差量 + 快照混合

1. 核心设计

服务器 EnTT 组件通过 Per-Component 脏标记追踪变化，Tick 末尾把变更的组件差量推送给各客户端。 同时定期发送完整快照作为客户端状态纠正的基线。快照间隔按 entity 类型差异化—— 高速移动 entity（坐骑/载具/冲锋）用更短的间隔防止可见的"拉回"效果。 差量优先写满 MTU，快照补发送未变更的数据。

🧠 设计哲学：服务器是权威状态（SSOT），客户端是缓存。服务器从不回答“我这个值对不对”，只主动告知“你现在的值是什么”。

2. 核心组件

组件职责
dirty_bitset (uint64_t)Per-Entity 的组件脏位掩码 (C++ 引擎层维护)
last_acked_version (uint32_t)客户端最后一次确认的快照版本号
replication_group (uint16_t)组件分组（高频 0 组、低频 1 组等）

3. 数据流

  C++ 引擎每 Tick 执行 ecs_stage "replicate"
  ┌─────────────────────────────────────────────────┐
  │                                               │
  │ 1. 收集 AoI 可见集 (GetWatchers)               │
  │    遍历所有玩家 Session 的 AOI 可见实体        │
  │                                               │
  │ 2. 差量打包 (Per-Player 写 MTU 上限)           │
  │    [entityId, dirty_flags, changed_fields...]   │
  │    优先写入：                                   │
  │      - 新进入 AoI 的实体 (全量)                 │
  │      - 离开 AoI 的实体 (OutOfRange)             │
  │      - 本 Tick 变脏的组件 (差量)                │
  │                                               │
  │ 3. 快照打包 (Per-Player 拆分包发送)             │
  │    每 4 Tick (200ms) 发送一次完整快照           │
  │    未变的数据不再序列化                         │
  │                                               │
  │ 4. 发送到客户端                                 │
  │    MSG_ENTITY_SYNC_NTF → session->Send()       │
  └─────────────────────────────────────────────────┘

4. 带宽预估 (Per Player, 100 个在 AOI 范围内)

场景差量 (每 Tick)快照 (200ms)平均带宽
平稳移动 (100 人 × Position dirty)~1.8 KB~12 KB~108 KB/s
激烈战斗 (50 人 × Pos/Velocity/HP dirty)~2.2 KB~12 KB~108 KB/s
无事件 (0 人 dirty)~50 B~12 KB~60 KB/s
📌 结论：差量 + 快照混合模型，玩家最大带宽 100-150 KB/s，远低于 1 MB/s 的家用宽带上限，预测无卡顿。

5. Proto 定义

message EntitySyncNtf {
    uint32 tick_id = 1;              // 服务器 Tick ID

    message EntityDelta {
      uint32 entity_id = 1;
      uint32 dirty_flags = 2;       // 位掩码: POSITION=1 | HEALTH=2 | ...
      repeated ComponentUpdate components = 3;
    }

    message ComponentUpdate {
      uint32 component_id = 1;      // 组件类型 ID
      bytes data = 2;               // 组件序列化数据（仅含变化字段）
    }

    repeated EntityDelta deltas = 2;          // 差量实体列表
    repeated uint32 create_entities = 3;      // 新进入 AoI 的实体（客户端需要创建）
    repeated uint32 destroy_entities = 4;     // 离开 AoI 的实体（客户端垃圾回收）
    repeated EntityDelta full_sync = 5;       // 全量快照（每 200ms）
    uint32 snapshot_version = 6;              // 快照版本号
  }

6. 脏标记生命周期

// C++ 引擎层——每当组件被修改时自动置脏
struct DirtyTracker {
    std::unordered_map<Entity, uint64_t> dirtyEntities;  // entity -> 脏位掩码
    std::unordered_set<Entity> createdEntities;       // 本 Tick 新创建的实体
    std::unordered_set<Entity> destroyedEntities;      // 本 Tick 已销毁的实体

    void MarkDirty(Entity entity, uint32_t componentBit);
    void MarkCreated(Entity entity);
    void MarkDestroyed(Entity entity);

    // 复制结束后清空所有脏标记
    void ClearAll();
  };

8. 优先级与带宽管理

当 MTU 不足以容纳所有脏实体时，按优先级排序发送：

优先级实体类型说明
1 (最高)新进入 AoI (Create)客户端必须立刻知道这个实体存在
2离开 AoI (Destroy)立即释放客户端资源
3玩家自己的 Entity核心体验（位置/HP 即时反馈）
4其他玩家 (PVP)PVP 目标——位置必须及时
5战斗怪物PVE 目标——HP 必须及时
6 (最低)远距 NPC / 装饰可推迟到下一个 Tick

9. 快照间隔差异化

不是所有 entity 都需要同样的快照纠错频率。静止 NPC 200ms 全量快照完全浪费带宽， 而飞行坐骑（30m/s）200ms 后位置偏差可达 6m——客户端纠错时产生明显"拉回"。 按 entity 的动态属性采用阶梯式快照间隔：

档位间隔适用 entityPCU 占比估算
默认200ms玩家步行、NPC、静止 entity~80%
高速100ms坐骑、载具、飞行、游泳~15%
战斗高速50ms冲锋/闪现技能施放中、PvP 竞技场内~5%
// ReplicationConfig.h — 快照间隔查表
struct ReplicationInterval {
    static constexpr int kDefault      = 200;
    static constexpr int kFastMoving   = 100;
    static constexpr int kCombatDash   = 50;
};

int GetSnapshotInterval(Entity e, const entt::registry& reg) {
    auto ent = entt::entity(e.EntityId());

    // 战斗高速：冲锋/闪现技能施放中
    if (reg.all_of<ChargingTag>(ent) || reg.all_of<DashingTag>(ent))
        return ReplicationInterval::kCombatDash;

    // 高速移动：坐骑/载具/飞行
    if (reg.all_of<MountTag>(ent) || reg.all_of<VehicleTag>(ent))
        return ReplicationInterval::kFastMoving;

    return ReplicationInterval::kDefault;
}

// 带宽影响估算（10000 PCU，每 player 可见 100 entity）
// 80% × 200ms + 15% × 100ms + 5% × 50ms
// ≈ 加权平均 ~170ms 等效间隔 → 带宽增幅 < 18%
📌 带宽影响：差异化快照的总带宽增幅 < 18%——大部分 entity 还是 200ms。 换来的是消除高速 entity 的"拉回"体验、竞技场 PvP 的状态准确性。 如果不实施差异化，200ms 全量快照对 PvE MMO 也可以工作——但在 PvP 和高速移动场景会有体感问题。

10. 客户端预测与服务器和解

客户端必须本地立即响应操作，否则 100ms RTT 意味着每次按键后 100ms 才看到角色响应。 采用 MMO 经典的 Server-authoritative + Client-side Dead Reckoning 方案。

核心流程

客户端：输入 → 立即更新本地位置（乐观预测）
  ├── 记录 pending moves（未确认的移动序列 + 时间戳）
  ├── 周期发送 MoveReq{ seqNum, input_direction, timestamp }（15Hz）
  └── 渲染预测位置

服务器：
  ├── 收到 MoveReq → NavMesh 校验（速度/可达性/碰撞）
  ├── 广播权威位置给 AOI 内所有人（通过差量复制）
  └── 回包 MoveRsp{ seqNum, server_position, timestamp }

客户端收到 MoveRsp：
  ├── 移除已确认的 pending moves（seqNum ≤ rsp.seqNum 的）
  ├── 从服务器位置开始重放未确认的 moves
  │   ├── 位置误差 ≤ 0.5m → 平滑 lerp 纠正（100ms 插值）——几乎无感
  │   └── 位置误差 > 3m  → 立即 snap + 记录 anomaly ——可能是外挂/瞬移
  └── 最大 pending 3 个 moves（覆盖 ~200ms 未确认窗口）

参数配置

参数值说明
预测发送频率25Hz（~40ms）配合 20ms Tick 的移动变化率
最大 pending moves3覆盖 ~200ms 的未确认窗口
平滑纠正阈值0.5m差值小于此值时 lerp 纠正（无感知）
立即 Snap 阈值3m差值大于此值时直接 teleport（异常/瞬移）
De-sync 告警阈值1m超过此值时记录 Tracy 标记（用于调优）
为何不做客户端回滚预测（Rollback）？ Overwatch / Valorant 等竞技 FPS 使用完整的预测 + 回滚（server reconciliation with rewind）， 但这需要服务器能"时光倒流"到过去的帧状态来重校验——对 MMO 来说过度工程化。 Dead Reckoning 的插值纠正足以应对 MMO 的移动同步精度需求。

11. 断线重连：完整状态恢复

断线重连不仅是连接恢复（§7b 的 Gate 15s 迁移窗口）——还需要恢复客户端的游戏状态。 15 秒断线期间世界仍在运转：AoI 内 entity 移动了、Boss 放技能了、Buff 到期了。 重连时需要把世界状态同步回客户端。

分档策略：短断线 vs 长断线

断线时长恢复策略客户端行为
短断线（< 5s） 增量恢复：客户端保留旧缓存，服务器补发 dirty entity 差量（从 last_acked_tick 到当前） 无 loading，差量到达后自动恢复渲染
长断线（5-15s，迁移窗口） 全量重建：服务器走 loading screen 流程，复用 §20 StateSnapshot 逻辑发送全量同步 loading screen（~0.5s）→ 重建 → 恢复
超时（> 15s） 迁移窗口过期 → session 已清理 → 需要重新走 LoginServer 踢回登录界面

重连流程

客户端 → Gate_2 → WorldServer: MSG_LOGIN_ENTER_WORLD_REQ { SessionToken }
  │
WorldServer 验证 Token → 找到 session:
  │
  ├── 短断线（distance < 5s）:
  │     MSG_RECONNECT_QUICK_NTF {
  │       tick_id: 当前 tick,
  │       self_sync: EntitySyncNtf（自己组件的 dirty delta）
  │       aoi_sync:  EntitySyncNtf（AoI 内 dirty entity 的差量）
  │     }
  │     → 客户端保留旧缓存 → 应用差量 → 无缝恢复
  │
  └── 长断线（5-15s）:
        MSG_RECONNECT_FULL_NTF {
          tick_id: 当前 tick,
          self_sync: EntitySyncNtf（自己全部组件——全量）
          aoi_entities: [EntitySyncNtf × N]（AoI 内所有 entity 的全量）
          scene_id: 当前场景
        }
        → 客户端 loading screen → 清空缓存 → 重建 → 恢复

关键事件的补发（断线期间产生）:
  ✅ 自己的 HP/MP/Position/BuffList — 全量同步
  ✅ AoI 内 entity 的当前位置/状态
  ✅ 邮件通知、GM 消息（从 MailMgr 重拉）
  ✅ 交易结果（服务端缓存最近一次交易状态）
  ⬚ 世界频道聊天 — 丢弃（发送频率高、丢失可接受）
  ⬚ 好友上线/下线通知 — 丢弃（下次状态查询自然同步）
  ⬚ 远处 NPC 移动 — 丢弃（差量自然覆盖）
实现复用：长断线的全量重建直接复用 §20 跨场景迁移的 StateSnapshot 机制—— 序列化/反序列化实体状态的代码不改。只是不涉及场景变更。 短断线的增量恢复直接复用 §3 的差量复制引擎——last_acked_tick → current_tick 的 dirty entity 集合。
📌 业界参考：TrinityCore 的 UpdateObject 机制也是差量 + 快照混合（UPDATETYPE_VALUES / CREATE_OBJECT / OUT_OF_RANGE_OBJECTS）。 本方案进一步细化了 Per-Component 脏位 + 带宽优先级 + 差异化快照 + 客户端预测 + 断线分层重连的工程实现。
