20. EntityId 编码方案

20.1 Entity 组件

// Entity.h
struct Entity {
    static constexpr uint32_t kSceneGlobal     = 0;
    static constexpr uint32_t kScenePersistent = 0xFFFFFFFF;

    uint64_t id;  // 高32位 = sceneId, 低32位 = EnTT entity id

    uint32_t SceneId()  const { return uint32_t(id >> 32); }
    uint32_t EntityId() const { return uint32_t(id & 0xFFFFFFFF); }

    static Entity Make(uint32_t sceneId, uint32_t entityId) {
        return Entity{(uint64_t(sceneId) << 32) | entityId};
    }

    auto operator<=>(const Entity&) const = default;
};

// hash 支持——用于 unordered_set / unordered_map
namespace std {
    template<> struct hash<Entity> {
        size_t operator()(const Entity& e) const { return e.id; }
    };
}

20.2 EnTT entity 位宽

EnTT 4.0 默认 uint32_t entity，20bit index + 12bit version。支持同时存在最多 ~1M 实体。内部 version 由 EnTT 自动管理——entity 被销毁回收后 version 自增，旧 Entity 引用失效。

📌 命名说明：本项目的 Entity 结构体（sceneId + entityId 的 64 位复合键）与 EnTT 内部的 entt::entity（uint32_t typedef）不是同一类型。 桥接层在调 EnTT API 时做显式转换：entt::entity(we.EntityId())。这两者不会冲突——Entity 是 Mserv 层的概念，entt::entity 是 EnTT 库内的概念。

20.3 Entity 生命周期

操作结果
ecs_create(sceneId)Scene.EcsRegistry().create() → EnTT 分配 entity id + 初始 version → 包装为 Entity
ecs_destroy(entity)Scene.EcsRegistry().destroy(entityId) → entity 进 free list，version 自增 → BlobStorage 同步清理
ecs_valid(entity)Scene.EcsRegistry().valid(entityId) → EnTT 校验 index + version 是否匹配
⚠ 跨场景迁移：旧 entity 被 destroy，新 Registry 执行 create 生成新 entity id。外部的旧 Entity 引用自动失效（version 不匹配），需同步更新所有引用方。

20.4 跨场景实体迁移：Clone 过渡方案

当实体从一个场景迁移到另一个场景（如玩家从主城进入副本），采用 Clone 过渡模式。 源场景创建实体的镜像引用（只读 Clone），目标场景逐步接管实体控制权。 过渡完成后源场景的 Clone 自动销毁。

迁移时序

Player 在 Scene_A 触发跨场景移动 (Portal / Teleport)
  │
  ├── 1. 冻结阶段（停止 Player 的输入处理）
  │     ecs_emplace(player, FrozenTag{})
  │
  ├── 2. 序列化阶段 Scene_A
  │     Scene_A: 收集所有组件数据（Position, Health, Inventory, Buffs...）
  │     → 序列化为 StateSnapshot（JSON blob + 二进制）
  │
  ├── 3. 迁移阶段 Scene_A→Scene_B
  │     Scene_B: 创建新 Entity（全新 entityId）
  │     Scene_B: 反序列化 StateSnapshot → 重建所有组件
  │     如果序列化/反序列化失败 → 留在 Scene_A，解除冻结
  │
  ├── 4. Clone 阶段（双 Scene 共存，60s 内）
  │     Scene_A: 旧 entity + DeprecatedTag（只读镜像，不可操作）
  │     Scene_B: 新 entity（活跃、可操作）← DasLang 侧更新引用
  │     GateServer: 更新路由表 → player 的消息转发到 Scene_B
  │
  ├── 5. 清理阶段（60s 或所有引用方已更新）
  │     Scene_A: 监测 DeprecatedTag + 60s 超时 → destroy 旧 entity
  │     Scene_B: 监测 FrozenTag → 移除 → 解冻 Player 输入
  │
  └── 6. 通知客户端
        MSG_SCENE_SWITCH_RSP(sceneId=Scene_B, newEntityId, position)

核心数据结构

// StateSnapshot.h — 跨场景迁移的序列化载体
struct StateSnapshot {
    uint32_t version = 1;

    // 组件数据（键值对——组件名 → 序列化数据）
    std::unordered_map<uint32_t, std::string> components;  // componentBit → JSON blob

    // 脚本 BlobStorage 数据
    std::unordered_map<std::string, std::vector<uint8_t>> scriptComponents;

    // 定时器恢复信息
    std::vector<TimerSnapshot> timers;  // 恢复未到期的定时器

    // 序列化/反序列化
    std::string Serialize() const;
    bool Deserialize(const std::string& data);
  };

批量迁移处理

战场结束（80 人同时迁回主城）、公会集结（40 人同时迁往副本）等场景 如果全在同一帧内做序列化/反序列化/创建 entity，将造成严重的 CPU spike。 采用分批迁移策略——每 Tick 最多处理 K 个 entity（K=8）， 超出部分排入迁移队列，后续 Tick 继续处理。 

// MigrationManager.h — WorldServer 层面维护迁移队列
class MigrationManager {
    static constexpr size_t kMaxPerTick = 8;
    static constexpr auto kTimeout = std::chrono::seconds(30);

    struct MigrationEntry {
        Entity entity;
        uint32_t sourceScene;
        uint32_t targetScene;
        std::chrono::steady_clock::time_point queuedAt;
    };

    std::deque<MigrationEntry> _pending;

public:
    void Enqueue(Entity e, uint32_t src, uint32_t dst);
    void ProcessTick();   // 在 LogicThread 每 Tick 调用
};

void MigrationManager::ProcessTick() {
    size_t count = 0;
    auto now = std::chrono::steady_clock::now();

    while (!_pending.empty() && count < kMaxPerTick) {
        auto& entry = _pending.front();

        if (now - entry.queuedAt > kTimeout) {
            LOG_WARN("Migration timeout for entity");
            ForceCleanup(entry);   // 超时清理
            _pending.pop_front();
            continue;
        }

        if (!DoMigrate(entry))     // 目标 Scene 未就绪？等待下个 Tick
            break;

        _pending.pop_front();
        count++;
    }
}
用户体验：80 人战场结束 → 每 Tick 8 人 → 最慢的 entity 需等 10 Tick ≈ 330ms。 客户端显示 "正在传送..." loading UI 即可完全掩盖。单个玩家切地图（非批量场景）不受影响——队列为空时一步完成。

DasLang 侧使用

// DasLang 侧——GM 传送 或 Portal 触发迁移
def MigrateEntityToScene(entity : Entity; targetSceneId : uint32) : Entity
{
    // 1. 冻结
    ecs_emplace(entity, type<FrozenTag>, FrozenTag{})

    // 2. 序列化
    let snapshot = ecs_snapshot_export(entity)

    // 3. 在目标场景创建新实体
    let newEntity = ecs_create(targetSceneId)
    ecs_snapshot_import(newEntity, snapshot)

    // 4. 标记旧实体为 Clone（等待清理）
    ecs_emplace(entity, type<DeprecatedTag>, DeprecatedTag{expireTime = GetTickTime() + 60.0})

    return newEntity
}

回滚场景

如果步骤 3 创建新实体失败（目标场景不存在、内存不足），回滚流程：

if (newEntity == InvalidEntity) {
    // 失败回滚——留在原场景
    ecs_remove(entity, type<FrozenTag>)
    SendToClient(entity, MSG_SCENE_SWITCH_RSP, BuildErrorResponse("destination unreachable"))
    return InvalidEntity
}
