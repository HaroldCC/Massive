17. 寻路与移动校验

17.1 NavMesh 库：Recast/Detour

离线用 Recast 烘焙场景 .obj → .navmesh 二进制文件。运行时 Detour 加载 .navmesh 做 A* 寻路 + 射线检测。 支持多层地形（楼梯/桥梁/洞穴）、动态障碍（临时阻挡）、多 Agent 类型（步行/飞行/游泳）。 WoW、Unreal Engine、Unity NavMesh 底层都用 Recast/Detour。

工具阶段输出
Recast离线烘焙（美术场景导出后）scene_1001.navmesh
Detour运行时加载 + 查询路径点列表 / 射线检测结果

17.3 NavMesh 数据管理

class NavMeshManager {
public:
    bool Load(uint32_t sceneId, const std::string& filePath);  // Scene 创建时调用
    void Unload(uint32_t sceneId);                            // Scene 销毁时调用

    // 寻路 — A* 返回完整路径点
    std::vector<Vector3> FindPath(uint32_t sceneId,
                                 const Vector3& from, const Vector3& to,
                                 int maxIters = 0);  // 0 = 不限迭代，>0 = 分帧

    // 射线检测（开发期调试用）
    bool Raycast(uint32_t sceneId,
                 const Vector3& from, const Vector3& to);

    // 点是否在 NavMesh 上
    bool IsOnNavMesh(uint32_t sceneId, const Vector3& point);

private:
    std::unordered_map<uint32_t, dtNavMesh*> _navMeshes;
    std::unordered_map<uint32_t, dtNavMeshQuery*> _queries;
};

17.4 寻路缓存策略

静态缓存：NPC 巡逻路径、打卡点间预计算一次，后续复用。动态分帧：怪物追击玩家时分帧计算 A*（每 Tick 限制 maxIters），不卡 Tick。

17.5 移动校验：全权服务器校验

之前的方案在步骤 ③ 用 Raycast 做穿墙检测——这对直线移动足够了，但对曲线路径（绕墙走）不成立。 修正后的方案：用 FindPath 验证路径可达性，而非简单 Raycast。 

Client → MSG_MOVE_REQ(targetX, targetY, targetZ)
  │
  ├── ① IsOnNavMesh(from) && IsOnNavMesh(to) ?
  │       任一不在 NavMesh 上 → MOVE_RSP(rejected, "not on navmesh")
  │
  ├── ② 距离检查: dist(from, to) ≤ maxSpeed × dt × tolerance(1.2) ?
  │       超过最大移速 → rejected ("speed hack suspected")
  │       tolerance=1.2 容忍网络抖动和客户端预测误差
  │
  ├── ③ FindPath(from, to) 返回非空路径 ?
  │       路径不可达（穿墙/跨越不可行走地形）→ rejected ("no valid path")
  │
  ├── ④ 路径合理性检查: pathLength ≤ dist(from, to) × 2.0 ?
  │       路径长度异常（弯曲程度超过 2 倍直线距离）→ rejected ("path too long")
  │
  └── ⑤ 全部通过 → 更新 Position → 标记脏 → 广播 Nearby → MOVE_RSP(accepted)
步骤校验内容阻止的作弊类型
①起点和终点都在 NavMesh 上飞天（y 坐标异常高）、遁地（y 坐标异常低）
②移动距离 ≤ 最大速度 × 时间加速挂、瞬移挂
③起点到终点可达穿墙（直接穿过不可行走区域）
④路径长度合理绕远路绕过 distance 检查（3D 空间绕行后路径极长）
⚠ 性能注意：FindPath 每次调用的成本约为 0.1-0.5ms（取决于路径长度和 NavMesh 复杂度）。 每 Tick 有 500-1000 个移动玩家时，总寻路开销约为 50-500ms，超出 50ms Tick 预算。 缓解策略：只对移动请求做 FindPath 校验，不是每个 entity 每 Tick 都校验。 玩家发 MSG_MOVE_REQ 的频率远低于每 Tick（通常每秒 4-10 次）。500 个在线玩家 × 每秒 5 次 = 每秒 2500 次 FindPath，单次 0.1ms = 250ms/s，分摊到 20 个 Tick 后每 Tick 约 12.5ms，可接受。

17.6 DasLang 桥接 API

// C++ 侧注册给 DasLang — 3 个函数
CheckCanMove(sceneId: uint32; fromX, fromY, fromZ: float; toX, toY, toZ: float): bool
FindPath(sceneId: uint32; fromX, fromY, fromZ: float; toX, toY, toZ: float): array<Vector3>
IsOnNavMesh(sceneId: uint32; x: float; y: float; z: float): bool

// DasLang 侧使用
def HandleMoveRequest(player : Entity; targetX : float; targetY : float; targetZ : float)
{
    let pos = ecs_get(player, type<Position>)
    if !CheckCanMove(currentSceneId, pos.x, pos.y, pos.z, targetX, targetY, targetZ)
    {
        SendToClient(player, MSG_MOVE_RSP, BuildRejectResponse("invalid move"))
        return
    }
    ecs_set(player, type<Position>, Position{targetX, targetY, targetZ})
    BroadcastMoveToNearby(player, targetX, targetY, targetZ)
}
