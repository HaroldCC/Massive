19. 配置数据热更新

19.1 热更新范围：配置表 + 脚本

技能模板、道具模板、怪物配置、活动参数等（PersistentRegistry 数据）支持热重载，不重启服务器。 DasLang 脚本文件变化 → 原生热重载（Context::relocateCode()）。 C++ 引擎、EnTT Component 定义、DB Schema 走停机维护。

19.2 热更新流程

GM 指令: /reload_config skill_templates
  │
  ▼
PersistentScene::ReloadTable("skill_templates")
  │
  ├── 1. 从 DB 加载新版数据到临时 buffer
  │     table("skill_templates") |> where_($(r) => r.is_active == true) |> to_array()
  │
  ├── 2. 校验新版数据合法性
  │     - 必填字段非空检查
  │     - 数值范围检查（CD ≥ 0, 伤害 ≥ 0）
  │     - 引用完整性检查（关联的 buff_id 在 buff_templates 中存在）
  │
  ├── 3. 校验通过 → 原子 swap
  │     swap(oldData, newData) — 旧数据保留作为回退备份
  │
  ├── 4. 广播配置变更事件
  │     ecs_dispatch("on_config_reloaded", "skill_templates")
  │     → DasLang 各系统收到通知 → 惰性清理缓存 / 全量刷新
  │
  └── 5. 校验失败 → 记录 ERROR 日志 + 返回错误给 GM + 保留旧数据不变

19.3 安全保证

  • 原子替换：新数据加载到独立 buffer，校验通过后一次 swap。swap 是 O(1) 指针交换，不出现"半更新"状态。
  • 旧数据回退：旧数据保留在 swap 后的 buffer 中。如果新配置导致大量 ERROR，GM 可以 /reload_config rollback 切回旧版本。
  • 版本号追踪：每张配置表有 config_version 字段。客户端可通过版本号对比决定是否需要更新本地缓存。
  • 不影响运行中数据：配置热重载只改配置表内存副本，不影响已创建的 Entity、已执行的逻辑。新逻辑从下次调用开始生效。

19.3.1 Schema 变更限制：只允许数值热重载

热重载只允许修改字段值（如：火球伤害 100 → 120），不允许结构变更（新增/删除/重命名字段）。 结构变更是"版本更新"，应配合 WorldServer 重启滚动更新。 这是业界标准做法——95% 的策划热更新需求只是改数值。

变更类型热重载？说明
修改字段值✅ 允许火球伤害 100→120、CD 10s→8s、掉落率 5%→8%
新增表行✅ 允许新增技能 ID=999——不是改 schema，是增行
新增字段（nullable）❌ 拒绝skill_templates 新增 min_range——需 WorldServer 重启
删除字段❌ 拒绝删除 mana_cost_percent——需 WorldServer 重启
修改字段类型❌ 拒绝cooldown int→float——需 WorldServer 重启
重命名字段❌ 拒绝castTime→cast_time_ms——需 WorldServer 重启
// ConfigTable.h — 热重载安全校验
struct HotReloadValidator {
    static bool CanHotReload(const ConfigSchema& oldS, const ConfigSchema& newS) {
        for (auto& oldField : oldS.fields) {
            auto it = newS.fields.find(oldField.name);
            if (it == newS.fields.end()) return false;  // 字段被删除
            if (it->type != oldField.type) return false;  // 类型被修改
        }
        return true;  // 只允许新增 nullable 字段——不破坏旧结构
    }
};

void ReloadConfig(const std::string& tableName) {
    auto newData = LoadFromDB(tableName);
    if (HotReloadValidator::CanHotReload(_currentSchema[tableName], newData.schema)) {
        _tables[tableName].AtomicSwap(newData);
        LOG_INFO("ConfigTable {} reloaded: {} rows", tableName, newData.rows);
    } else {
        LOG_WARN("ConfigTable {} schema changed — needs WorldServer restart", tableName);
    }
}

19.4 副作用处理

策略适用表实现
惰性更新 技能模板、道具模板、掉落表 收到 on_config_reloaded 事件后清空相关缓存。下次使用时从新模板重新加载。
全量刷新 活动开关、功能开关 立即遍历所有受影响的 Entity 应用新配置（分帧执行避免卡 Tick）。 
// DasLang 侧 — 事件监听
[export]
def InitConfigReloadHandlers()
{
    ecs_listen("on_config_reloaded") $(var tableName : string)
    {
        if (tableName == "skill_templates") {
            ClearSkillCache()
        } elif (tableName == "event_config") {
            // 活动开关——立即刷新所有 NPC
            for sceneId in GetAllSceneIds() {
                ecs_query(sceneId; npc : NPCTag&; event : EventParticipant&) {
                    RefreshNpcEventState(npc, event)
                }
            }
        }
    }
}

19.5 配置数据存储：DB 为权威来源

配置表存储在 PostgreSQL 中（item_templates、skill_templates、monster_templates 等）。 运营工具直接用 SQL 更新配置。WorldServer 启动时从 DB 加载全部配置到 PersistentRegistry，运行中通过 GM 指令热重载。

表名内容热重载触发
item_templates道具名称、类型、属性、icon、售价/reload_config item_templates
skill_templates技能名称、CD、消耗、伤害公式、Buff 关联/reload_config skill_templates
monster_templates怪物 HP、攻击、掉落表、AI 类型、刷新时间/reload_config monster_templates
quest_templates任务条件、奖励、对话文本/reload_config quest_templates
event_config活动开关、时间窗口、参与条件、奖励倍率/reload_config event_config

19.6 DasLang 脚本热更新

GM 指令 /reload_script skill_fireball → C++ 调用 Context::relocateCode() → 重新编译指定的 .das 模块 → 新函数指针替换旧函数。正在执行的旧版本调用不受影响，新调用走新版。
