21. 部署运维概览 · 5 进程一步到位

21.1 构建系统：xmake

所有 5 种进程共享同一个 xmake.lua，DBWorkerPool 在 common 库中。

-- xmake.lua
set_project("Massive")
set_languages("c++23")
add_rules("mode.debug", "mode.release")

add_requires("entt v4.0.0", "asio", "protobuf-cpp",
             "spdlog", "openssl", "recastnavigation",
             "tomlplusplus", "tracy", "libpq")

option("tracy", {default = false, description = "Enable Tracy profiler"})

-- 公共库（被所有进程链接）——含 DBWorkerPool + DBRange + DirtyTracker
target("massive_common")
    set_kind("static")
    add_files("src/common/**.cpp")
    add_packages("entt", "asio", "protobuf-cpp",
                 "spdlog", "openssl", "recastnavigation",
                 "tomlplusplus", "libpq")

-- 🔄 Schema → C++ 代码生成（构建前自动执行）
task("gen-db-bindings")
    on_run(function()
        os.exec("python tools/generate_db_bindings.py --config config/world_1.toml")
    end)

-- 5 个独立进程
target("LoginServer")
    set_kind("binary")
    add_files("src/login/**.cpp")
    add_deps("massive_common")

target("GateServer")
    set_kind("binary")
    add_files("src/gate/**.cpp")
    add_deps("massive_common")

target("WorldServer")
    set_kind("binary")
    add_files("src/world/**.cpp")
    add_deps("massive_common")

target("CenterServer")
    set_kind("binary")
    add_files("src/center/**.cpp")
    add_deps("massive_common")

target("SocialServer")
    set_kind("binary")
    add_files("src/social/**.cpp")
    add_deps("massive_common")

-- DasLang 模块
target("module_entt")
    set_kind("shared")
    add_files("src/ecs/ModuleEntt.cpp")
    add_packages("entt")

  config/                # 各进程 TOML 配置文件
  data/navmesh/          # Recast 烘焙的 .navmesh 文件
  scripts/               # DasLang 脚本（AI, Skill, Quest, GM...）
  tools/
    generate_db_bindings.py  # 🔄 Schema → C++ 代码生成器（连接 PG → information_schema → autogen/）

🔄 代码生成自动化：CMake/xmake 中配置 add_custom_command——检测 common/db/autogen/ 目录的修改时间 vs migrations/ 目录的修改时间。如果 migrations 更新了，自动重跑 generate_db_bindings.py 再编译。日常开发不需要手动跑脚本。

21.5 部署策略：渐进式

根据项目规模分阶段升级部署方案——不提前投资不需要的复杂度。

阶段 1：开发环境 — Docker Compose

# docker-compose.yml — 本地开发一键启动
services:
  postgres:   { image: postgres:16, ports: ["5432:5432"] }
  pgbouncer:  { image: edoburu/pgbouncer, ports: ["6432:6432"] }

  center:  { build: ., command: ./CenterServer, depends_on: [pgbouncer] }
  social:  { build: ., command: ./SocialServer, depends_on: [pgbouncer] }
  world:   { build: ., command: ./WorldServer,  depends_on: [pgbouncer, center, social] }
  gate:    { build: ., command: ./GateServer,   depends_on: [world], ports: ["9000:9000"] }
  login:   { build: ., command: ./LoginServer,  depends_on: [pgbouncer, world], ports: ["8443:8443"] }

Docker Compose 仅用于本地开发和内测阶段（0-500 人），不适合生产。

阶段 2：测试/生产（初期）— systemd + Ansible

每台物理机直接跑进程，systemd 管理生命周期——这是传统游戏公司（Blizzard、TrinityCore 私服等）的标准做法。 

/etc/systemd/system/
  center-server.service
  social-server.service
  world-server@.service    (模板实例: world-server@1, world-server@2)
  gate-server@.service
  login-server.service

# 批量部署——Ansible playbook
ansible-playbook -i inventory/production deploy.yml
# → scp 二进制 → systemctl restart → 健康检查
systemd 能力覆盖项
Restart=always进程崩溃自动重启
WatchdogSec=30s无心跳自动 kill + restart
journald日志集中收集

此方案足够支撑到数万 PCU——复杂性低，运维透明。

阶段 3：生产（规模扩大后）— k8s 升级路径

当 WorldServer 实例数扩展到 16+、运维人力充足时，可升级到 Kubernetes： 

k8s 部署：
  Deployment/LoginServer  (replicas: 2)
  DaemonSet/GateServer    (每节点一个，hostNetwork)
  StatefulSet/WorldServer (replicas: N, StatefulSet 保留 pod 标识)
  StatefulSet/CenterServer (replicas: 1, 主备通过 etcd 选主)
  StatefulSet/SocialServer (replicas: 2)
  PgBouncer → Service → ExternalName 指向外部 PG
  服务发现：Consul DNS 或 k8s Service DNS

21.7 进程崩溃恢复

进程恢复策略
LoginServer无状态。systemd Restart=always。新实例立即可用。
GateServer无状态。客户端自动切换到下一个 gateIP。systemd 自动重启。
WorldServer有状态（场景数据）。Crash 后从 DB 场景快照恢复（§15.7）。systemd Restart=always。
CenterServer有状态（服务注册表）。主备切换（§28）。
SocialServer有状态。数据在 PG。重启后从 DB 重载。

21.8 反外挂：多层检测框架

服务器权威架构（SSOT）已免疫大部分客户端外挂——内存修改、数据包篡改、穿墙瞬移均被 §17 的 NavMesh 校验 + AES-GCM 加密阻断。但 Bot/脚本外挂发送的每个操作都是"合法的"（合法的移动距离、 合法的技能释放）——必须通过行为检测来识别。

第 1 层：服务端权威校验（已有设计）

校验项实现位置违规处理
移动速度 ≤ 1.2x 最大速度§17 移动校验拒绝移动
目标在 NavMesh 可达区域§17 NavMeshManager拒绝移动
技能 CD 已就绪§24 SkillCooldown拒绝施法
拾取距离 ≤ 拾取范围§26 物品系统拒绝拾取
背包空间足够§26 背包系统拒绝获得物品

第 2 层：Token Bucket 频率限制 + Suspicion Score

// AntiCheat.h — 轻量实时异常检测
class AntiCheat {
    struct PlayerMetrics {
        TokenBucket moveBucket{20, 20};     // 20/s 移动操作
        TokenBucket skillBucket{10, 10};   // 10/s 技能释放
        TokenBucket lootBucket{5, 5};      // 5/s 拾取操作
        int suspicionScore = 0;
    };

    bool CheckOperation(Entity player, OperationType op) {
        auto& m = _metrics[player];
        if (!m.GetBucket(op).TryConsume()) {
            m.suspicionScore += 1;
            if (m.suspicionScore > 100) {
                KickPlayer(player, "suspicious activity detected");
                LOG_WARN("ANTICHEAT: player {} flagged, score={}", player, m.suspicionScore);
                return false;
            }
            return false;  // 拒绝超频操作
        }
        if (m.suspicionScore > 0)
            m.suspicionScore--;  // 衰减——正常操作逐渐恢复信誉
        return true;
    }
};
检测维度人类特征Bot 特征检测方式
操作频率按需，有波动恒定高频、无疲劳Token Bucket 限频
在线时长≤16h/天24h 连续≥24h → 强制下线 15min
操作间隔方差有自然抖动近乎完美恒定间隔未来阶段实现（需离线分析）
移动路径有微偏差NavMesh 最优直线未来阶段实现（需离线分析）

第 3 层：离线经济/行为分析（公测阶段按需建设）

第 1+2 层覆盖 80% 常见外挂检测。第 3 层（经济异常、多账号关联、物品流转图分析） 需要专门的数据管道和 GM 审核团队——在公测阶段按需建设。

21.9 灰度发布（Canary）

当前阶段（开发/内测）：全量部署 + systemd 自动重启。 PCU < 500 时灰度发布是过度工程化。

公测前实施：Gate 版本路由 + 逐台 WorldServer 滚动更新。 C2 拓扑天然支持逐台替换——Gate 根据后端容量路由，WorldServer 之间不直接通信。 

滚动更新流程（公测版）：
  ├── 1. 编译新版本二进制
  ├── 2. 选择 1 台 WorldServer → systemctl stop → 替换二进制 → start
  ├── 3. 该 WorldServer 向 CenterServer 注册（携带版本号）
  ├── 4. GateServer 优先将新登录的玩家路由到新版 WorldServer
  ├── 5. 已在旧版 World 上的玩家保持旧版（不强制迁移）
  ├── 6. 观察 15 分钟（/metrics: 错误率、CPU、内存）
  │   ├── 正常 → 逐台重启剩余 WorldServer
  │   └── 异常 → 杀掉新版 → rollback 二进制 → 新连接回到旧版
  └── 7. 全部升级完成 → 旧版本废弃
兼容性约束：为支持将来的灰度发布，现在开始遵守两个约束—— Proto 字段只追加不删除（protobuf 天然支持），Entity 组件只新增不重命名。 这样新旧版本在通信和数据格式上可以共存。
